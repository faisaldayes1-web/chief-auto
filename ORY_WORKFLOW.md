## Execute through one workflow
Approved game intent → relevant departments → owned outcome package → qualified worker/tools → integrated accepted result. “Build a game” starts authorized implementation; advice uses the same grounding without dispatch. Small tasks inherit project decisions. Existing task boards/issues remain live authority; do not create a competing queue or restart work to fill a template.

Reuse suitable existing code/assets before creating new systems. Select a tool for the actual outcome and record source versions, invocation/output evidence, consumer and remaining limitations. Installation or queue delivery is not acceptance. Retain current engine and working implementations unless the actual approved task requires change.

## Visual and narrative continuity
Use the game's approved Visual target and canon first. The UI reference library is optional when layout/hierarchy/readability needs examples; adapt useful qualities to the existing art style, camera and controls. Do not restyle a game based on an external screenshot or infer new mechanics from a concept. Compare actual results during ordinary integration; no separate early engine experiment or mandatory playable visual benchmark.

## Preserved authority
All existing file/task ownership, approvals, holds, paid-credit limits, protected-game restrictions, required review and release rules remain in force. Historical vendor/department descriptions do not grant ownership or forbid an otherwise authorized capable worker; actual task claims govern. This update does not activate agents, schedules or relays and does not authorize changing another owner's files. Report tests honestly, including waived or unperformed checks.

Document migration is not proof of fresh runtime qualification. Keep the actual changed behavior, exact candidate and source-bound acceptance in the existing handoff.
